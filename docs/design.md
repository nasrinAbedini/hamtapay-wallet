# طراحی فنی سیستم کیف پول همتاپی

## ۱. معرفی پروژه

هدف، پیاده‌سازی یک سیستم کیف پول ریالی با قابلیت‌های زیر است:

- ایجاد کیف پول برای کاربر در اولین استفاده
- مشاهده موجودی کیف پول
- شارژ کیف پول از طریق درگاه پرداخت (PSP)
- شارژ دستی کیف پول توسط مدیر
- برداشت ریالی به شماره شبا
- ثبت تمام عملیات مالی در دفترکل دوطرفه (Double-entry Ledger)
- جلوگیری از ثبت عملیات مالی تکراری
- جلوگیری از موجودی منفی
- کنترل سقف برداشت روزانه

### تکنولوژی‌های انتخاب‌شده

- Backend: NestJS + TypeScript
- Database: PostgreSQL
- Architecture: Modular Monolith
- API Documentation: Swagger / OpenAPI
- Testing: Integration Test با PostgreSQL واقعی

# ۲. فرضیات سیستم (Assumptions)

برای طراحی سیستم، فرضیات زیر در نظر گرفته شده‌اند:

1. مدیریت کاربران و احراز هویت خارج از محدوده این پروژه است.
2. شناسه کاربر از بیرون سیستم دریافت می‌شود و نیازی به جدول Users نداریم.
3. کیف پول هر کاربر هنگام اولین استفاده ایجاد می‌شود.
4. واحد پول ریال در API و دیتابیس بر اساس تومان محاسبه می‌شود.
5. مبلغ ریالی عدد صحیح است و اعشار ندارد.
6. در صورت موفقیت پرداخت PSP، موجودی کیف پول افزایش پیدا می‌کند.
7. Callback درگاه پرداخت به‌تنهایی قابل اعتماد نیست و باید پرداخت از PSP استعلام شود.
8. Timeout سرویس Payout به معنی ناموفق بودن برداشت نیست.
9. سقف برداشت روزانه هر کاربر ۲۰۰ میلیون تومان است.
10. تاریخ محاسبه سقف روزانه بر اساس منطقه زمانی `Asia/Tehran` است.
11. PostgreSQL منبع اصلی و معتبر اطلاعات مالی سیستم است.

---

# ۳. معماری و مرز ماژول‌ها (Module Boundaries)

معماری پروژه از نوع Modular Monolith است.

در این معماری، تمام ماژول‌ها در یک برنامه NestJS قرار دارند، اما مسئولیت‌های مشخص و مستقل دارند.

### ۳.۱ Wallet Module

مسئولیت‌ها:

- ایجاد کیف پول در اولین استفاده
- دریافت موجودی کیف پول
- مدیریت موجودی قابل برداشت (Available)
- مدیریت موجودی رزروشده (Reserved)
- جلوگیری از منفی شدن موجودی

### ۳.۲ Ledger Module

مسئولیت‌ها:

- ثبت تمام عملیات مالی
- پیاده‌سازی Double-entry
- کنترل توازن Debit و Credit
- نگهداری تاریخچه تغییرات مالی
- جلوگیری از تغییر یا حذف سوابق مالی

### ۳.۳ Payment Module

مسئولیت‌ها:

- ایجاد درخواست شارژ کیف پول
- ارتباط با PSP
- دریافت Callback
- استعلام و تأیید پرداخت
- افزایش موجودی کیف پول پس از تأیید پرداخت

در این طراحی، جدول جداگانه‌ای به نام `deposits` نداریم. اطلاعات درخواست‌های شارژ در جدول `payments` ذخیره می‌شوند.

### ۳.۴ Withdrawal Module

مسئولیت‌ها:

- ثبت درخواست برداشت
- بررسی موجودی
- کنترل سقف برداشت روزانه
- رزرو مبلغ برداشت
- ارتباط با سرویس Payout
- مدیریت وضعیت برداشت
- آزادسازی مبلغ در صورت شکست قطعی

### ۳.۵ Adjustment

ماژول و جدول جداگانه‌ای برای Adjustment در نظر نمی‌گیریم.

افزایش دستی موجودی توسط مدیر از طریق API داخلی انجام می‌شود و نتیجه آن مستقیماً در Wallet و Ledger ثبت می‌شود.

### ۳.۶ Idempotency

مسئولیت‌ها:

- جلوگیری از اجرای تکراری درخواست‌های مالی
- تشخیص استفاده مجدد از یک کلید با اطلاعات متفاوت
- برگرداندن پاسخ قبلی برای درخواست تکراری

### ۳.۷ Payment Integration

ارتباط با سرویس‌های خارجی از طریق لایه Adapter انجام می‌شود.

این لایه شامل ارتباط با:

- PSP
- Payout Service

است.

# ۴. طراحی دیتابیس (Database Design)

در طراحی اولیه از ۶ جدول استفاده می‌کنیم:

1. wallets
2. ledger_entries
3. payments
4. withdrawals
5. idempotency_keys

در واقع ۵ جدول اصلی داریم؛ جدول ششم یا جدول جداگانه‌ای برای مدیریت سقف روزانه لازم نیست، چون اطلاعات آن از withdrawals محاسبه می‌شود.

## ۴.۱ جدول wallets

نگهداری موجودی کیف پول کاربران.

| ستون | نوع | توضیح |
|---|---|---|
| id | UUID | کلید اصلی |
| user_id | UUID | شناسه کاربر |
| currency | VARCHAR(10) | واحد پول |
| available_balance | NUMERIC(20,6) | موجودی قابل استفاده |
| reserved_balance | NUMERIC(20,6) | موجودی رزروشده |
| created_at | TIMESTAMP | زمان ایجاد |
| updated_at | TIMESTAMP | زمان بروزرسانی |

محدودیت‌ها:

- هر کاربر برای هر ارز فقط یک کیف پول دارد.
- ترکیب `user_id` و `currency` یکتا است.
- موجودی قابل استفاده و رزروشده نباید منفی شود.
- موجودی IRR باید عدد صحیح باشد.

ایندکس:

```sql
UNIQUE (user_id, currency)
```

برای عملیات مالی روی کیف پول از `SELECT FOR UPDATE` استفاده می‌کنیم تا درخواست‌های هم‌زمان باعث تغییر نادرست موجودی نشوند.

## ۴.۲ جدول ledger_entries

این جدول مهم‌ترین بخش سیستم مالی است.

تمام عملیات مالی باید به شکل Double-entry در این جدول ثبت شوند.

| ستون | نوع | توضیح |
|---|---|---|
| id | UUID | کلید اصلی |
| transaction_id | UUID | شناسه گروه تراکنش مالی |
| account_code | VARCHAR(50) | نوع حساب |
| related_user_id | UUID | شناسه کاربر مرتبط |
| reference_type | VARCHAR(50) | نوع مرجع |
| reference_id | VARCHAR(100) | شناسه مرجع |
| amount | NUMERIC(20,6) | مبلغ |
| currency | VARCHAR(10) | واحد پول |
| entry_type | VARCHAR(10) | DEBIT یا CREDIT |
| created_by_type | VARCHAR(20) | SYSTEM یا MANAGER |
| created_by_id | UUID | شناسه ایجادکننده |
| description | TEXT | توضیحات |
| created_at | TIMESTAMP | زمان ثبت |

### مفهوم Account

در این طراحی جدول جداگانه‌ای به نام `accounts` نداریم.

نوع حساب با `account_code` مشخص می‌شود.

مقادیر مورد استفاده:

- USER_WALLET_AVAILABLE
- USER_WALLET_RESERVED
- PSP_CLEARING
- PAYOUT_CLEARING
- ADJUSTMENT_CLEARING

برای حساب‌های کاربری، `related_user_id` مشخص‌کننده صاحب حساب است.

برای حساب‌های سیستمی، مقدار آن NULL خواهد بود.

### قوانین Ledger

1. هر رویداد مالی حداقل دو Entry دارد.
2. مجموع Debit و Credit برای هر `transaction_id` و هر ارز باید برابر باشد.
3. مبلغ هر Entry باید مثبت باشد.
4. Entryها پس از ثبت نباید ویرایش یا حذف شوند.
5. اصلاح تراکنش فقط با ثبت تراکنش اصلاحی انجام می‌شود.
6. تمام Entryهای مربوط به یک رویداد مالی، `transaction_id` یکسان دارند.

نکته: توازن Debit و Credit در سرویس مالی قبل از Commit کنترل می‌شود. در نسخه‌های بعدی می‌توان این کنترل را با Deferred Constraint Trigger در PostgreSQL نیز اجباری کرد.

ایندکس‌ها:

```sql
CREATE INDEX idx_ledger_transaction_id
ON ledger_entries(transaction_id);

CREATE INDEX idx_ledger_related_user
ON ledger_entries(related_user_id, created_at);

CREATE INDEX idx_ledger_reference
ON ledger_entries(reference_type, reference_id);
```

## ۴.۳ جدول payments

این جدول درخواست‌های شارژ کیف پول از طریق PSP را نگهداری می‌کند.

در این طراحی جدول `deposits` حذف شده و Payment مسئول مدیریت فرآیند شارژ است.

| ستون | نوع | توضیح |
|---|---|---|
| id | UUID | کلید اصلی |
| user_id | UUID | شناسه کاربر |
| amount | NUMERIC(20,6) | مبلغ پرداخت |
| currency | VARCHAR(10) | واحد پول |
| status | VARCHAR(30) | وضعیت پرداخت |
| psp_token | VARCHAR(255) | توکن PSP |
| order_id | VARCHAR(100) | شناسه سفارش |
| provider_ref_id | VARCHAR(100) | شناسه مرجع پرداخت |
| created_at | TIMESTAMP | زمان ایجاد |
| updated_at | TIMESTAMP | زمان بروزرسانی |

محدودیت‌ها:

- مبلغ باید مثبت باشد.
- `psp_token` در صورت وجود باید یکتا باشد.
- `order_id` باید یکتا باشد.

ایندکس‌ها:

```sql
CREATE UNIQUE INDEX idx_payments_psp_token
ON payments(psp_token)
WHERE psp_token IS NOT NULL;

CREATE INDEX idx_payments_user_created
ON payments(user_id, created_at);
```

### فرآیند شارژ کیف پول

1. کاربر درخواست شارژ ارسال می‌کند.
2. یک Payment با وضعیت PENDING ایجاد می‌شود.
3. درخواست به PSP ارسال می‌شود.
4. کاربر به درگاه پرداخت هدایت می‌شود.
5. PSP نتیجه پرداخت را Callback می‌کند.
6. سیستم پرداخت را از PSP استعلام و تأیید می‌کند.
7. در صورت موفقیت، در یک Database Transaction:
   - موجودی Wallet افزایش پیدا می‌کند.
   - دو Entry در Ledger ثبت می‌شود.
   - وضعیت Payment به SUCCEEDED تغییر می‌کند.

اگر پرداخت ناموفق باشد، وضعیت Payment به FAILED تغییر می‌کند و موجودی کیف پول تغییری نمی‌کند.

**نکته:** Callback تکراری نباید باعث افزایش دوباره موجودی شود.

## ۴.۴ جدول withdrawals

نگهداری درخواست‌های برداشت کاربران.

| ستون | نوع | توضیح |
|---|---|---|
| id | UUID | کلید اصلی |
| user_id | UUID | شناسه کاربر |
| amount | NUMERIC(20,6) | مبلغ برداشت |
| currency | VARCHAR(10) | واحد پول |
| destination | VARCHAR(255) | شماره شبا |
| status | VARCHAR(30) | وضعیت برداشت |
| provider_request_id | VARCHAR(100) | شناسه درخواست Payout |
| created_at | TIMESTAMP | زمان ایجاد |
| updated_at | TIMESTAMP | زمان بروزرسانی |

محدودیت‌ها:

- مبلغ باید مثبت باشد.
- `provider_request_id` در صورت وجود باید یکتا باشد.
- وضعیت برداشت باید معتبر باشد.

ایندکس‌ها:

```sql
CREATE UNIQUE INDEX idx_withdrawals_provider_request
ON withdrawals(provider_request_id)
WHERE provider_request_id IS NOT NULL;

CREATE INDEX idx_withdrawals_user_date_status
ON withdrawals(user_id, created_at, status);
```

### کنترل سقف برداشت روزانه

جدول `daily_withdrawal_usage` را حذف می‌کنیم.

برای محاسبه مجموع برداشت‌های روزانه از جدول `withdrawals` استفاده می‌کنیم.

منطق:

1. ردیف Wallet کاربر با `SELECT FOR UPDATE` قفل می‌شود.
2. مجموع برداشت‌های همان کاربر در روز جاری محاسبه می‌شود.
3. برداشت‌های با وضعیت زیر در محاسبه لحاظ می‌شوند:
   - PENDING
   - PROCESSING
   - UNKNOWN
   - SUCCEEDED
4. برداشت‌های FAILED محاسبه نمی‌شوند.
5. مبلغ درخواست جدید به مجموع اضافه می‌شود.
6. اگر مجموع از ۲۰۰ میلیون تومان بیشتر باشد، درخواست رد می‌شود.

این محاسبه و ثبت برداشت در یک Database Transaction انجام می‌شود.

قفل Wallet باعث می‌شود درخواست‌های هم‌زمان یک کاربر به ترتیب بررسی شوند و چند درخواست نتوانند هم‌زمان از سقف باقی‌مانده استفاده کنند.

## ۴.۵ جدول idempotency_keys

برای جلوگیری از اجرای تکراری عملیات مالی.

| ستون | نوع | توضیح |
|---|---|---|
| id | UUID | کلید اصلی |
| scope | VARCHAR(100) | محدوده عملیات |
| key | VARCHAR(255) | کلید Idempotency |
| request_hash | VARCHAR(255) | Hash درخواست |
| response | JSONB | پاسخ ذخیره‌شده |
| status | VARCHAR(20) | وضعیت پردازش |
| created_at | TIMESTAMP | زمان ایجاد |

محدودیت:

```sql
UNIQUE (scope, key)
```

قوانین:

- اگر درخواست با همان Key و همان اطلاعات ارسال شود، پاسخ قبلی برگردانده می‌شود.
- اگر همان Key با اطلاعات متفاوت استفاده شود، خطای IDEMPOTENCY_KEY_REUSED برمی‌گردد.
- درخواست در حال پردازش نباید دوباره اجرا شود.
- کنترل تکراری بودن با Unique Constraint دیتابیس انجام می‌شود، نه صرفاً با SELECT.

# ۵. رفتار مالی عملیات

## ۵.۱ شارژ کیف پول از PSP

فرض کنیم کاربر ۱۰۰ هزار تومان شارژ می‌کند.

در صورت تأیید پرداخت، دو Entry ثبت می‌شود:

| حساب | نوع | مبلغ |
|---|---|---:|
| PSP_CLEARING | DEBIT | 100,000 |
| USER_WALLET_AVAILABLE | CREDIT | 100,000 |

سپس موجودی قابل استفاده کیف پول افزایش پیدا می‌کند.

## ۵.۲ شارژ دستی توسط مدیر

API:

```http
POST /internal/adjustments
```

ورودی:

```json
{
  "userId": "uuid",
  "currency": "IRR",
  "amount": "100000",
  "reason": "Manual wallet top-up"
}
```

در یک Database Transaction:

1. کیف پول کاربر قفل می‌شود.
2. موجودی افزایش پیدا می‌کند.
3. دو Entry در Ledger ثبت می‌شود.
4. اطلاعات مدیر و دلیل عملیات در Ledger ذخیره می‌شود.

نمونه Ledger:

| حساب | نوع | مبلغ |
|---|---|---:|
| ADJUSTMENT_CLEARING | DEBIT | 100,000 |
| USER_WALLET_AVAILABLE | CREDIT | 100,000 |

برای شارژ دستی، نیازی به جدول Adjustment نداریم.

## ۵.۳ برداشت کیف پول

فرض کنیم کاربر درخواست برداشت ۵۰۰ هزار تومان دارد.

### مرحله اول: رزرو مبلغ

در یک Database Transaction:

1. Wallet قفل می‌شود.
2. موجودی قابل استفاده بررسی می‌شود.
3. سقف برداشت روزانه بررسی می‌شود.
4. Withdrawal با وضعیت PENDING ثبت می‌شود.
5. موجودی Available کاهش پیدا می‌کند.
6. موجودی Reserved افزایش پیدا می‌کند.
7. دو Entry در Ledger ثبت می‌شود.

نمونه Ledger:

| حساب | نوع | مبلغ |
|---|---|---:|
| USER_WALLET_AVAILABLE | DEBIT | 500,000 |
| USER_WALLET_RESERVED | CREDIT | 500,000 |

### مرحله دوم: ارسال درخواست به Payout

بعد از Commit شدن تراکنش دیتابیس، درخواست به سرویس Payout ارسال می‌شود.

فراخوانی سرویس خارجی نباید داخل Database Transaction انجام شود.

شناسه `provider_request_id` باید قبل از ارسال درخواست در دیتابیس ذخیره شده باشد.

### مرحله سوم: نتیجه برداشت

اگر Payout موفق باشد:

- موجودی Reserved کاهش پیدا می‌کند.
- تراکنش تسویه در Ledger ثبت می‌شود.
- وضعیت Withdrawal به SUCCEEDED تغییر می‌کند.

اگر Payout قطعاً ناموفق باشد:

- موجودی Reserved کاهش پیدا می‌کند.
- موجودی Available افزایش پیدا می‌کند.
- تراکنش اصلاحی در Ledger ثبت می‌شود.
- وضعیت Withdrawal به FAILED تغییر می‌کند.

اگر درخواست Timeout شود:

- وضعیت برداشت UNKNOWN می‌شود.
- مبلغ در Reserved باقی می‌ماند.
- مبلغ همچنان در محاسبه سقف روزانه لحاظ می‌شود.
- سیستم باید با استعلام مجدد وضعیت را مشخص کند.

# ۶. چرخه وضعیت‌ها (State Machine)

## ۶.۱ وضعیت Payment

```text
PENDING
   |
   v
PAYMENT_INITIATED
   |
   v
VERIFYING
   |
   +------------------+
   |                  |
   v                  v
SUCCEEDED           FAILED
```

توضیح وضعیت‌ها:

| وضعیت | توضیح |
|---|---|
| PENDING | درخواست پرداخت ایجاد شده |
| PAYMENT_INITIATED | درخواست به PSP ارسال شده |
| VERIFYING | در حال تأیید پرداخت از PSP |
| SUCCEEDED | پرداخت تأیید شده و موجودی افزایش یافته |
| FAILED | پرداخت ناموفق بوده است |

حالت‌های خطا:

- خطای ارتباط با PSP هنگام ایجاد پرداخت: درخواست با وضعیت مناسب خطا مدیریت می‌شود و پرداخت موفق تلقی نمی‌شود.
- Callback تکراری: عملیات مالی دوباره اجرا نمی‌شود.
- Callback نامعتبر: درخواست رد می‌شود.
- عدم تطابق مبلغ پرداخت: پرداخت تأیید نمی‌شود.
- Timeout هنگام استعلام: وضعیت تا زمان تعیین تکلیف، VERIFYING باقی می‌ماند.
- پرداخت ناموفق: وضعیت FAILED می‌شود.

## ۶.۲ وضعیت Withdrawal

```text
PENDING
   |
   v
PROCESSING
   |
   +------------------+
   |                  |
   v                  v
SUCCEEDED           FAILED
   |
   |
   +------------------

PROCESSING
   |
   v
UNKNOWN
   |
   +------------------+
   |                  |
   v                  v
SUCCEEDED           FAILED
```

توضیح وضعیت‌ها:

| وضعیت | توضیح |
|---|---|
| PENDING | درخواست ثبت شده و مبلغ رزرو شده |
| PROCESSING | درخواست به Payout ارسال شده |
| UNKNOWN | نتیجه درخواست نامشخص است |
| SUCCEEDED | برداشت با موفقیت انجام شده |
| FAILED | برداشت قطعاً ناموفق بوده است |

حالت‌های خطا:

- موجودی ناکافی: درخواست با خطای INSUFFICIENT_FUNDS رد می‌شود.
- سقف برداشت بیشتر از حد مجاز: DAILY_LIMIT_EXCEEDED
- مبلغ کمتر از حداقل: BELOW_MINIMUM
- شماره شبا نامعتبر: INVALID_DESTINATION
- Timeout سرویس Payout: وضعیت UNKNOWN و حفظ مبلغ رزروشده
- شکست قطعی Payout: آزادسازی مبلغ رزروشده و ثبت تراکنش اصلاحی
- Callback تکراری: بدون تغییر دوباره موجودی
- خطای دیتابیس: کل تراکنش Rollback می‌شود.

وضعیت‌های SUCCEEDED و FAILED نهایی هستند و نباید دوباره تغییر کنند.

# ۷. تراکنش‌های دیتابیس (Database Transactions)

تمام عملیات مالی باید به شکل اتمیک انجام شوند.

یعنی اگر یکی از مراحل عملیات شکست بخورد، تمام تغییرات همان عملیات Rollback شوند.

### عملیات شارژ

در یک تراکنش:

- افزایش موجودی Wallet
- ثبت Ledger
- تغییر وضعیت Payment

### عملیات برداشت

در یک تراکنش:

- قفل Wallet
- بررسی موجودی
- بررسی سقف روزانه
- ایجاد Withdrawal
- انتقال موجودی Available به Reserved
- ثبت Ledger
- ثبت نتیجه Idempotency

### عملیات شارژ دستی

در یک تراکنش:

- قفل Wallet
- افزایش موجودی
- ثبت Ledger
- ثبت اطلاعات مدیر و دلیل عملیات

### نکته مهم

هیچ درخواست خارجی مانند PSP یا Payout نباید داخل Database Transaction اجرا شود.

# ۹. تصمیم‌های معماری (ADR)

## ADR-001: استفاده از Double-entry Ledger

### مسئله

چگونه صحت تراکنش‌های مالی و قابلیت حسابرسی را تضمین کنیم؟

### گزینه‌ها

1. نگهداری فقط موجودی کیف پول
2. نگهداری تاریخچه تراکنش‌ها بدون Double-entry
3. استفاده از Double-entry Immutable Ledger

### تصمیم

استفاده از Double-entry Ledger.

### دلیل انتخاب

- تمام عملیات مالی قابل ردیابی هستند.
- توازن Debit و Credit قابل بررسی است.
- اصلاح تراکنش‌ها بدون حذف سابقه انجام می‌شود.
- امکان حسابرسی و بررسی مغایرت‌ها وجود دارد.

### هزینه انتخاب

پیچیدگی بیشتر در طراحی و پیاده‌سازی و نیاز به کنترل توازن تمام تراکنش‌ها.

---

## ADR-002: استفاده از Modular Monolith

### مسئله

آیا سیستم را از ابتدا به شکل Microservices طراحی کنیم؟

### گزینه‌ها

1. Microservices
2. Modular Monolith

### تصمیم

استفاده از Modular Monolith با NestJS.

### دلیل انتخاب

- محدودیت زمانی پروژه
- کاهش پیچیدگی Deployment
- مدیریت ساده‌تر تراکنش‌های مالی
- امکان توسعه مستقل ماژول‌ها در داخل یک برنامه

### هزینه انتخاب

ماژول‌ها مستقل Deploy نمی‌شوند و منابع اجرایی و دیتابیس مشترک دارند.

---

## ADR-003: حذف جدول‌های اضافی و محاسبه مستقیم اطلاعات

### مسئله

آیا برای مدیریت سقف برداشت روزانه و شارژ کیف پول به جدول‌های جداگانه نیاز داریم؟

### گزینه‌ها

برای سقف روزانه:
1. ایجاد جدول daily_withdrawal_usage
2. محاسبه مجموع برداشت‌ها از جدول withdrawals

برای شارژ:
1. ایجاد جدول deposits
2. استفاده از جدول payments

### تصمیم

- حذف daily_withdrawal_usage
- حذف deposits
- استفاده از withdrawals برای محاسبه سقف روزانه
- استفاده از payments برای مدیریت درخواست شارژ

### دلیل انتخاب

- کاهش تعداد جدول‌ها
- کاهش پیچیدگی کد
- جلوگیری از نگهداری اطلاعات تکراری
- مناسب بودن برای محدوده زمانی پروژه

### هزینه انتخاب

محاسبه مجموع برداشت‌ها با Query انجام می‌شود و با افزایش تعداد برداشت‌ها ممکن است هزینه Query بیشتر شود.

در صورت افزایش حجم سیستم، می‌توان جدول Aggregate جداگانه‌ای برای سقف روزانه اضافه کرد.

---

## ADR-004: فراخوانی Payout خارج از Database Transaction

### مسئله

چگونه با سرویس خارجی Payout ارتباط برقرار کنیم؟

### گزینه‌ها

1. فراخوانی سرویس خارجی داخل Database Transaction
2. فراخوانی سرویس بعد از Commit
3. استفاده از Transactional Outbox

### تصمیم

در نسخه اولیه، درخواست Payout بعد از Commit شدن تراکنش دیتابیس ارسال می‌شود.

### دلیل انتخاب

- جلوگیری از باز ماندن تراکنش دیتابیس هنگام انتظار برای سرویس خارجی
- کاهش پیچیدگی پیاده‌سازی
- مناسب بودن برای زمان محدود پروژه

### هزینه انتخاب

اگر برنامه بعد از Commit و قبل از ارسال درخواست متوقف شود، Withdrawal در وضعیت PENDING باقی می‌ماند.

بنابراین باید امکان شناسایی و پردازش مجدد درخواست‌های باقی‌مانده وجود داشته باشد.

در نسخه‌های بعدی می‌توان Transactional Outbox را اضافه کرد.

## وضعیت پیاده‌سازی و اصلاح فرضیات

این بخش مرجع پیاده‌سازی فعلی است و اختلاف‌های متن بالا را روشن می‌کند:

- تعداد جدول‌های اصلی پنج مورد است، نه شش: `wallets`، `ledger_entries`، `payments`، `withdrawals` و `idempotency_keys`.
- ارز ریالی در API با کد `IRR` و مبلغ صحیح بر حسب تومان نمایش داده می‌شود. اعداد اعشاری فقط برای `USDT` مجازند؛ برداشت این نسخه فقط IRR است.
- schema فقط از migration نسخه‌دار ساخته می‌شود و TypeORM synchronization خاموش است. trigger دیتابیس، update/delete روی ledger را رد می‌کند.
- برای جلوگیری از تکرار مالی، درخواست concurrent با همان idempotency key پاسخ `IDEMPOTENCY_IN_PROGRESS` می‌گیرد. خطاهای HTTP نهایی نیز برای همان کلید ذخیره می‌شوند. خطای فرایندی ناشناخته ممکن است کلید را در حالت IN_PROGRESS باقی بگذارد؛ پاک‌سازی خودکار ندارد.
- خروجی API و تاریخچه از مقادیر Decimal رشته‌ای PostgreSQL استفاده می‌کنند و محاسبات سقف و موجودی با integer arithmetic انجام می‌شوند.
- Adapterها از قرارداد `hamtapay/t103-simulator:1.0` استفاده می‌کنند. کد داخل archive سیمولاتور بررسی شده است؛ تست زنده انجام نشده چون بارگذاری Docker در این نشست رد شد. مسیرها، codeهای تأیید PSP و webhook payout در `provider-notes.md` ثبت شده‌اند.
- manager access در این نسخه با secret ثابت محیطی و `x-manager-id` پیاده شده است؛ سامانه احراز هویت کاربران و مدیران خارج از محدوده است.
- برای عملیات Payout، endpointهای manager-protected بررسی وضعیت و بازیابی برداشت‌های PENDING و PROCESSING قدیمی وجود دارد. webhook امضاشده simulator در `/webhooks/payout` پذیرفته می‌شود. بازیابی باید توسط scheduler یا عملیات دستی فراخوانی شود، چون Outbox وجود ندارد.
- وضعیت `RETURNED` از simulator پس از تسویه پشتیبانی می‌شود و با migration افزایشی به schema اضافه شده است؛ مبلغ به کیف پول Available برمی‌گردد و Ledger جبرانی ثبت می‌شود.
- آدرس‌های داخلی callback در Compose به `app:3000/payments/psp/callback` و `app:3000/webhooks/payout` تنظیم شده‌اند. آدرس base simulator برای هر دو adapter `http://simulator:8080` است.
- تست‌های integration به PostgreSQL واقعی نیاز دارند. تست‌های Jest در این نشست به‌دلیل نبود `TEST_DATABASE_URL` رد شدند؛ simulator image نیز به‌دلیل رد شدن درخواست Docker اجرا نشد.
